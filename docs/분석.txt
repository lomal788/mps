원본 프로그램을 분석해서 웹으로 포팅하려고 한다.
원본의 동작·데이터·계산·상태 수명을 상세히 분석하고, 다른 개발자나 AI가 해당 문서만으로 구현을 이어갈 수 있도록 Markdown 파일로 정리해 저장해줘.

[프로젝트 정보]
- 서비스/게임 이름: {이름}
- 원본 소스·실행 파일·데이터 위치: {경로}
- 기존 분석 자료: {경로}
- 웹 프로젝트 위치: {경로 또는 아직 없음}
- 분석 문서 저장 위치: {경로}
- 우선 분석할 기능: {기능}
- 참고할 실제 동작·화면·증상: {설명}

[목표]
단순히 원본에 어떤 기능이 있는지 나열하는 것이 아니라,
그 기능을 웹에서 재현할 수 있을 만큼 구체적인 구현 명세를 만들어줘.

핵심 질문은 다음과 같다.
1. 어떤 입력·이벤트·상태에서 기능이 시작되는가?
2. 어떤 데이터와 계산을 사용하는가?
3. 어떤 순서와 주기로 실행되는가?
4. 어떤 상태를 변경하고 다른 기능에 어떤 영향을 주는가?
5. 언제 종료·취소·초기화·복구되는가?
6. 화면·애니메이션·이펙트·소리와 어떻게 연결되는가?
7. 웹에서는 어떤 구조로 구현해야 원본 동작을 재현할 수 있는가?

[이번 작업의 범위]
우선 원본 분석과 MD 문서 작성에 집중해줘.
웹 구현을 별도로 요청하지 않았다면 서비스 소스는 변경하지 마.
분석에 필요한 추출·검증 스크립트와 결과 파일은 저장해도 된다.
원본 파일은 변경하지 말고 기존 작업도 보존해줘.

[분석 진행 방법]
1. README·작업 지침·기존 분석 문서를 읽고 원본 자료와 도구의 위치를 확인해줘.
2. 기존 분석 결과를 활용하되 확정 사실·추정·미확정을 구분해줘.
3. 기능의 진입점부터 호출자·피호출자·데이터 로더·최종 소비자까지 추적해줘.
4. 원본 소스가 없으면 바이너리의 명령·문자열·참조·가상함수·구조체 접근을 근거로 분석해줘.
5. 관련 에셋과 설정 파일도 찾아 코드와 연결해줘.
6. 핵심 함수만 떼어 보지 말고 기능의 전체 수명을 분석해줘.
7. 현재 자료로 추가 확인이 가능하면 계속 추적하고, 첫 번째 불명확한 지점에서 끝내지 마.

[반드시 확인할 내용]

A. 실행 흐름
- 생성·초기화·로딩·시작·갱신·종료·해제
- 호출 순서와 호출 주기
- 프레임 단위와 고정 스텝 단위의 구분
- 입력 이벤트와 실제 처리 시점
- 조기 반환·우회·예약·지연 실행
- 동일 프레임에 여러 조건이 성립할 때 우선순위

B. 상태와 데이터
- 클래스·구조체·필드·열거형·비트 플래그
- 필드 타입·크기·오프셋·초기값·단위
- 값을 쓰는 함수와 읽는 함수
- 상태 전이 조건과 종료 조건
- 이전 값·캐시·래치·누적값의 수명
- 데이터의 소유권·공유 범위·초기화 시점
- 클라이언트·서버·원격 객체의 역할 차이

C. 계산과 조건
- 실제 공식·상수·계수
- 기본값·설정값·가산/대입·우선순위
- 좌표계·축 방향·회전 규약
- 시간·속도·거리 등의 단위
- 정수·f32·f64와 반올림·절삭 순서
- 경계값·클램프·예외 처리
- 상태·모드·환경·데이터에 따른 분기

D. 표현과 리소스
- 애니메이션·이펙트·소리·카메라의 연결
- 리소스 ID·이름·파일 위치·선택 조건
- 재생 시점·반복·전환·중단·복구
- 논리 상태와 화면 표현의 관계
- 물리에 영향을 주는 변환과 시각 전용 변환의 구분
- 모델·텍스처·재질·설정 파일의 로딩 구조

E. 다른 기능과의 연결
- 입력 차단·이벤트 중첩·모드 변경
- 충돌·이동·네트워크·복귀·일시정지 등과의 상호작용
- 다른 함수가 나중에 덮어쓰거나 소비하는 값
- 단독 함수는 맞아도 호출 순서 때문에 결과가 달라지는 부분

[웹 포팅 명세]
분석한 원본 동작마다 아래 내용을 작성해줘.

- 웹에서 필요한 모듈과 책임
- 상태 객체와 데이터 구조
- 입력·출력 인터페이스
- 초기화와 업데이트 순서
- 구현 가능한 수준의 의사코드
- 원본 변수·필드와 웹 권장 이름의 대응표
- 사용할 실제 값·단위·기본값
- 필요한 에셋 변환·추출 과정
- 브라우저·서버에서 공유해야 할 로직
- 원본과 동일하게 유지해야 하는 순서·정밀도·조건
- 웹 환경 때문에 구현 방식을 바꿔야 하는 부분과 동등성 유지 방법
- 검증용 입력과 기대 결과

웹 권장 이름은 원본에서 확인된 이름과 구분해 표시해줘.
근거가 부족한 부분에 임의의 값이나 동작을 채워 넣지 마.

원본보다 자연스럽거나 현대적인 구현을 제안하는 것이 목적이 아니다.
우선 원본의 관측 가능한 동작을 재현하는 것을 목표로 해줘.
원본의 특이한 계산이나 예외도 확인 없이 정리·삭제하지 마.

[검증]
가능하면 핵심 계산·상태 전이를 실제로 실행해 확인해줘.

- 동일 초기 상태와 입력으로 계산 결과 확인
- 정상·경계·반대 조건 검사
- 시작→유지→종료→재시작의 연속 실행
- 이벤트 중첩과 취소·복구
- 실제 데이터 표본을 사용한 검사
- 단일 함수와 여러 함수 연결 실행의 구분

원본 실행, 원본 명령 판독, 재구현 계산, 합성 테스트를 구분해줘.
스텁으로 대체한 함수와 그로 인해 검증되지 않은 범위를 적어줘.
함수 테스트 통과를 전체 프로그램 동작 검증으로 확대하지 마.

[MD 작성 방식]
분량이 크면 기능별 문서로 나누고 목차 문서에서 연결해줘.
같은 설명을 여러 문서에 복사하기보다는 근거 문서로 링크해줘.

각 기능 문서는 다음 구성을 기본으로 해줘.

1. 기능 개요와 사용자에게 보이는 동작
2. 분석 대상 원본·버전·자료 위치
3. 진입점과 전체 호출 흐름
4. 구조체·필드·상수·열거형 표
5. 상태 전이와 전체 수명
6. 계산식·조건·상세 의사코드
7. 애니메이션·이펙트·소리·카메라·에셋 연결
8. 다른 기능과의 상호작용
9. 웹 포팅 구조와 구현 순서
10. 검증 코드·실행 결과·기대값
11. 미확정 사항과 추가 분석에 필요한 근거

함수마다 파일 위치 또는 주소를 기록해줘.
필드마다 가능하면 writer와 reader를 함께 적어줘.
오프셋이 같은 서로 다른 구조체를 혼동하지 않도록 기준 객체를 명시해줘.

[확정 수준]
각 핵심 결론에 다음을 구분해 표시해줘.
- 원본 실행 확인
- 원본 코드/명령 판독 확인
- 데이터 확인
- 추정
- 미확정

“분석 완료”와 “웹 구현 완료”와 “동작 검증 완료”는 다른 상태다.
미확정 항목을 임의로 해결됨으로 바꾸지 마.
새 근거가 기존 결론을 뒤집으면 본문을 정정하고 이유를 남겨줘.

[마무리]
MD 파일을 실제로 저장하고 링크·주소·수치·상태 표기의 모순을 확인해줘.
최종 답변에는 다음을 간결하게 알려줘.

- 작성·업데이트한 문서 경로
- 확정한 핵심 동작
- 웹 포팅에 필요한 주요 구성요소와 구현 순서
- 실제 수행한 검증
- 남은 미확정 범위와 이유
- 원본/웹 소스 변경 여부
